# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RGF Rebate Scheme System — a React/Vite/TypeScript SPA for managing E-Motorcycle rebate applications across 8 roles (System Admin, E-Moto Company/applicant, Asset Financier, Rebate Analyst, Rebate Manager, E-Moto Program Manager, Designated Finance Officer, M&E Team/External Reviewer). Originated as a Figma Make project (see the autogenerated notice in `kv_store.tsx`) and has since been hand-built out considerably.

## Commands

- `npm run dev` — start Vite dev server on port 3000 (opens browser automatically)
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build
- `npm run deploy:server` — deploy the Supabase Edge Function (`make-server-324f6e20`) via `npx supabase functions deploy ... --no-verify-jwt`

There is no lint or test script configured (no ESLint config, no `tsconfig.json`, no test runner present), despite the README mentioning `npm run lint` — that script doesn't exist in `package.json`. Don't assume linting/type-checking commands work until tooling is actually added.

## Architecture

### Frontend: role-routed dashboards, no router library

`src/App.tsx` is the single entry point. After auth, it switch-renders one top-level dashboard component per `user.role` (e.g. `AnalystDashboard`, `AssetFinancierAdminDashboard`, `QADashboard` aliased as `RebateManagerDashboard`, `CFODashboard` aliased as `ProgramManagerDashboard`). "Page" navigation *within* a dashboard is simulated via a `currentPage` string passed down as a prop and an `onNavigate` callback — there is no React Router; each dashboard component internally decides what to render for a given `currentPage` value.

Role strings have accumulated both legacy lowercase values (`admin`, `applicant`, `analyst`, `qa`, `cfo`, `finance`, `management`) and newer UPPER_SNAKE values (`SYSTEM_ADMIN`, `REBATE_ANALYST`, `ASSET_FINANCIER_ADMIN`, etc.) from a role-model migration — `App.tsx` maps both old and new role strings to the same dashboards. When touching role-gating logic, check `src/utils/auth.tsx` (the `User.role` union) and `src/App.tsx`'s render branches together; they must stay in sync.

Dashboard components live under `src/components/<role-area>/` (`admin`, `applicant`, `analyst`, `asset-financier`, `cfo`, `finance`, `management`, `qa`). `src/components/ui/` holds the shadcn/Radix-based primitive component library (buttons, dialogs, tables, etc.) — treat these as generic building blocks, not feature code. `src/components/shared/` holds cross-role widgets.

### Backend: single Hono Edge Function + Postgres KV store

All backend logic lives in one Supabase Edge Function: `supabase/functions/make-server-324f6e20/index.tsx` (and a duplicate `index.ts` — the two files are currently identical; keep them in sync if editing, or ask whether one should be removed). It's a Hono app mounting routes under `/make-server-324f6e20/*` for auth, applications, criteria, permissions, financiers, disbursements, etc.

Most persistence goes through `kv_store.tsx`, a generic key-value wrapper (`get`/`set`/`del`/`mget`/`mset`/`getByPrefix`) over a single Postgres table `kv_store_324f6e20 (key TEXT PRIMARY KEY, value JSONB)` — this file is autogenerated/marked "DO NOT EDIT". Domain entities (applications, users, roles, permissions, notifications, etc.) are stored as JSON blobs under prefixed keys rather than in normalized tables. `seed.tsx` (2200+ lines) provides demo/seed data and is invoked from the login screen's "Seed Demo Data" button. `otp_service.tsx` handles OTP/2FA.

Auth is Supabase Auth (`supabase.auth`); the frontend calls the Edge Function with the session's bearer token for everything else (see `src/utils/auth.tsx` and `src/utils/api.tsx`'s `fetchWithAuth`). `src/utils/functionsBase.ts` resolves the function base URL, defaulting to `https://<projectId>.supabase.co/functions/v1/make-server-324f6e20`, overridable at runtime via `globalThis.__FUNCTIONS_BASE_URL__`.

### Permissions model

Two parallel-ish permission systems exist:
- `src/utils/permissions.ts` — a full RBAC model (`PermissionCategory`, `PermissionAction`, `Role`, `Permission`, `SystemRoles`, `SystemPermissions`) intended for fine-grained, admin-configurable permissions, exposed to the frontend via `src/hooks/usePermissions.tsx` and `authService.getUserPermissions()` (`GET /users/:id/effective-permissions`).
- `src/utils/afPermissions.ts` — a smaller, Asset-Financier-specific permission helper.

When adding permission checks, prefer the RBAC system (`usePermissions`) over hardcoding role-string comparisons where practical, though existing code frequently does direct `user.role === '...'` checks (see `App.tsx`).

### Path aliases

Vite is configured with `@` → `./src`, plus explicit aliases stripping version suffixes from imports (e.g. `sonner@2.0.3` → `sonner`) — a leftover from Figma Make's versioned-import convention. If you see an import like `from 'some-lib@1.2.3'` in a component, it resolves through this alias map in `vite.config.ts`, not a real package name; prefer the unversioned import going forward.

### Stray root-level documentation

`src/` contains dozens of historical status/summary/guide markdown files at its root (implementation reports, demo credential dumps, fix summaries, etc.). These are progress artifacts from earlier work sessions, not living documentation — don't treat them as authoritative for current behavior; check the actual component/route code instead. `DEMO_CREDENTIALS.md` / `CREDENTIALS.md` do contain the current demo login accounts referenced by `App.tsx`'s unrecognized-role fallback UI.
